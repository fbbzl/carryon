# Git 使用标准

项目 `AGENTS.md` 或仓库约定优先；本文件不强制分支模型、托管平台或团队流程。

## 提交

0. 单次提交只表达一个可理解、可验证的意图，不混入无关格式化或重构。
1. 提交信息遵循项目约定；未定义时优先使用 `type(scope): subject` 的 Conventional Commits 格式。
2. 提交正文说明重要原因、取舍和验证结果，不机械重复 diff。
3. Issue、需求或决策记录只在实际存在时关联。

## 分支与同步

0. 分支命名和数量服从项目规模；个人项目不强制 `develop`、release 或 hotfix 分支。
1. 同步前先确认工作树、目标分支和远端状态，避免覆盖未提交改动。
2. 已提交且粒度清晰的局部改动优先精确搬运；同源同步可 rebase，独立历史合流可 merge。
3. 已被他人依赖的历史不重写；确需 force push 时必须确认影响范围并使用安全保护选项。
4. 解决冲突后重新运行受影响验证，不能只以冲突标记消失作为完成依据。

## 审查与集成

0. 使用 PR 时，描述变更背景、范围、风险和验证；大小以能被有效审查为准，不设统一行数阈值。
1. Reviewer、CI 和合并方式由项目协作模式决定；个人项目和人工流程不强制虚构审批或自动化。
2. 未通过必要验证或仍有阻断风险的改动不得进入受保护分支或发布版本。

## 版本与恢复

0. 只有对外发布或需要追踪版本时才打标签；版本格式服从项目发布策略。
1. 出现问题时根据代码、数据和外部副作用选择 revert、前滚修复、功能关闭或恢复方案，不假设回滚总是安全。
2. 恢复操作记录原因、影响范围、版本和验证结果；禁止用历史重写掩盖已发布问题。
