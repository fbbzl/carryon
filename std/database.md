# 数据库设计标准

本标准适用于关系型数据库；具体命名、类型和能力以实际数据库、ORM 与项目约定为准。

## 数据模型与完整性

0. 先按业务不变量和访问模式建模；规范化是起点，有证据的反规范化是允许的。
1. 主键、唯一约束、外键或应用层校验应共同保证数据完整性；是否使用外键取决于一致性、迁移和运维约束。
2. 字符集、排序规则、时区和精度必须覆盖真实数据范围，并在关联字段间保持兼容。
3. 逻辑删除只在审计、恢复或业务语义需要时使用，并明确唯一约束、查询过滤和最终清理策略。
4. 命名遵循项目既有约定，不在跨项目标准中固定单复数、字段名或 ID 生成算法。

## 类型与约束

0. 金额和计量值使用满足精度要求的定点或整数类型，不使用会产生业务误差的浮点表示。
1. 时间字段明确时区、精度和业务语义，不用含糊字符串代替可查询的时间类型。
2. 枚举、JSON、大文本和二进制字段根据查询、约束和演进需求选择，不把结构化核心数据藏进不可验证字段。
3. 业务唯一性由数据库约束或同等强度的机制保证，不能只依赖前置查询。

## 索引与查询

0. 索引由真实查询、数据分布和执行计划驱动；不为每个字段机械建索引。
1. 联合索引顺序结合过滤、排序、范围条件和数据库规则决定，不只按区分度排序。
2. 查询只读取需要的数据；关联数量没有统一上限，以可读性、执行计划和延迟预算判断。
3. 避免无界循环 SQL 和 N+1；无法批量时明确规模、事务、并发和失败处理。
4. 分页必须有稳定排序；深分页、大批量读写和长任务根据测量结果采用游标、分批或后台处理。

## 事务与并发

0. 事务边界围绕需要原子保证的业务不变量设计，并保持尽可能短。
1. 默认避免在数据库事务中执行远程 I/O；确实无法避免时，限制超时并明确幂等、锁影响、补偿与失败恢复。跨系统一致性优先使用 Outbox 或项目既有机制。
2. 只读事务、隔离级别、乐观锁和悲观锁根据一致性目标与竞争情况选择。
3. 重试必须识别可重试错误并保证幂等，不能掩盖死锁、冲突或部分成功。

## 迁移与恢复

0. 生产结构和数据变更使用可审计、可重复的迁移方式，并记录适用版本。
1. 每次迁移必须说明恢复策略；可选择回滚、前滚、备份恢复或数据补偿，不假设所有迁移都可逆。
2. 破坏性变更采用兼容过渡，确认旧读写方退出后再清理；等待周期以真实发布节奏为准。
3. 同步更新受影响的实体、契约、映射、测试和文档，并验证迁移前后数据不变量。
4. 分区、分片和读写拆分由容量、增长、热点和查询证据触发，不使用统一行数阈值。
