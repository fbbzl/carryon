# 通用编码原则

本标准适用于所有语言和框架；项目规则和实际技术栈约定优先。

## 决策顺序

0. 正确性与安全性是硬门禁，不能用可读性、进度或性能换取。
1. 满足门禁后，优先级为 `可读性 > 可维护性与可扩展性 > 性能`。
2. 性能优化必须基于测量结果，并记录为此引入的复杂度。

## 核心原则

0. 简单：如无必要，勿增实体。
1. 合适：选择匹配当前约束的方案，不追逐新奇技术。
2. 可扩展：只为已知变化保留边界，不为假设需求预先设计。

## 工程不变量

0. 外部输入在信任边界校验；HTML、URL 等文本在输出点按上下文编码，SQL 使用参数绑定，OS 命令优先使用无 Shell 的参数 API 并限制允许范围。
1. 密钥、密码和 Token 不进入代码、日志、客户端、构建或部署产物。
2. 循环或批处理中避免无界逐条 I/O；无法批量时明确规模、并发、超时、重试和失败影响面。
3. 错误必须被处理、转换或传播，并在责任边界记录一次；不得静默吞掉。
4. 资源生命周期必须明确，异常、取消和超时路径也要释放资源。
5. 公共契约变更必须说明兼容、迁移或废弃路径。
6. 模块职责清晰、依赖单向；发现循环依赖时先检查边界设计。

## 代码质量信号

0. 方法长度、文件大小、嵌套层级、参数数量和圈复杂度是审查信号，不是统一硬阈值。
1. 使用有意义的命名；注释解释原因、约束和取舍，不复述代码。
2. 复杂流程在代码和测试仍不足以表达时，再补充必要的流程或决策说明。
3. 优先复用项目已有能力和成熟依赖；新增依赖或自建通用能力要说明必要性与维护成本。
4. 删除无用代码和失效配置，不保留没有迁移计划的兼容分支。

## 变更与验证

0. 验证范围与变更风险相称，至少覆盖修改路径和关键失败路径。
1. 重构保持外部行为时，用现有测试或补充的特征测试证明行为未变。
2. 代码、配置、契约、迁移和文档涉及同一变更时同步更新。
3. 变更结论至少绑定 `observed_at`、`reference_version`、`environment`、`verified_scope`、`unverified_scope`、`evidence`、`result` 和 `next_action`；轻量任务可合并表达，但不得省略未验证范围。
4. `evidence` 只引用已有 URL、仓库路径与行号、命令或日志、测试/构建/事件 ID，并注明结果；不得猜测 URL，无法取得时明确标为 `unknown` 并保留风险。
