# optimize

仅在 `cr` 将明确的优化审查项反馈给 `dev` 后，以其目标和验收条件为边界完成性能、容量、成本或资源效率优化。`dev` 负责实现与开发验证；`cr` 复审原审查项，`qa` 独立验证行为与回归，`dp` 决定发布和运行观察。

## 适用边界

- 唯一入口是 `cr -> dev` 的优化审查项，输入必须包含审查项 ID、证据、影响范围、目标和验收条件；缺项时回交 `cr` 补齐，不由 `dev` 自行扩大优化范围。
- 用户直接提出或 `dev` 自行识别的优化机会，在 `cr` 形成审查项前不调用本 Skill；可先将候选证据交给 `cr`。
- 目标至少明确一个主指标及其测量口径，例如延迟、吞吐、错误率、CPU/内存、查询量、网络调用、存储占用或单位成本，并有当前基线或可取得基线的路径。
- 明确负载模型、数据规模、环境、观测窗口、成功预算和不可接受的回归；无基线时先建立测量，再决定是否实施优化。
- 若优化会改变业务优先级、数据一致性等级、可用性承诺、外部契约、计费语义、权限、缓存一致性或异步交付语义，回到 `dev` 常规流程并在适用时升级 `survey-corps`。

## 图示对齐

当瓶颈跨越组件、队列、缓存、数据库或外部服务时，可用 Mermaid 或 ASCII 字符图描述关键路径、等待点和容量边界；图示不替代剖析、压测或运行证据。

## 优化闭环

1. 建立 Goal：记录主指标、基线、预算、负载模型、测量命令、环境、构建模式、样本量、噪声因素和退出条件；先确认应测 wall time、CPU time、吞吐、尾延迟还是资源用量。
2. 在代表性数据、硬件和 release/optimized 构建上定位瓶颈；基准包含必要预热和多次重复，优先使用 profile、Trace、指标或查询计划，将观察结果与猜测分开记录。
3. 选择最小策略：减少不必要工作、批处理、缓存、索引、并发控制、资源复用或算法/数据结构调整；说明一致性、超时、重试、容量和失效策略。
4. 以小切片实施：每个切片都可单独测量和回退，避免把格式化、重构和多项优化混为一个结果。
5. 在同等或已记录差异的环境中对照重测；条件允许时交错执行新旧版本以降低系统漂移，并报告中位数、尾部值和离散度，而非只比较一次或只看均值。
6. 达到预算、改进落入噪声/低于最小有意义阈值，或下一步会突破正确性、安全、复杂度、成本预算时停止；记录停止原因和残余瓶颈。

## 门禁与交接

- 只有达到预算且没有超出已声明的行为、正确性、安全、容量或成本回归，才可声明开发目标完成；样本不足、方差失控或无法同口径对比的结果只作为观察，不作为优化结论。
- 缓存、并发、批处理、降级和重试必须说明失效、背压、幂等性、超时和失败影响面；不得把压低错误率建立在吞错或丢数据上。
- 交回 `cr`：原审查项 ID、基线/后测数据、负载模型、策略、契约不变量、变更和复审证据；交给 `qa`：关键行为、性能回归场景和未验证范围；交给 `dp`：可观测性、容量假设、开关及回退输入。
