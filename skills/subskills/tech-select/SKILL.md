# tech-select

仅在 `dev` 与用户对齐实现方案且需要选择技术、库、组件或集成模式时，提供可追溯的选型建议。该 Skill 的结论是方案对齐输入，只有用户确认后才能进入实现；`survey-corps` 仍负责需跨角色裁决的高风险方案协议。

## 适用边界

- 唯一入口是 `dev <-> 用户` 的方案对齐；必须存在待用户决定或确认的候选方案。方案已确认、实现中的例行内部选择或单纯依赖升级不调用本 Skill。
- 先读取项目本地规范、现有依赖、运行环境、运维能力和已确认约束；已有标准能满足目标时默认复用，不为新颖性引入替代品。
- 目标明确为一个技术决策，例如客户端状态方案、序列化库、任务队列接入方式、缓存模式或观测组件；需求、验收和非目标已可界定。
- 若选项会新增运行平台或关键基础设施、改变安全/合规边界、处理敏感数据、引入付费或外部账户、变更数据库/迁移策略、公共 API 或发布模型，先将选项和风险升级 `survey-corps`，不得自行落地。

## 图示对齐

当候选方案的组件边界、数据流、部署形态或依赖方向影响判断时，可用 Mermaid 或 ASCII 字符图比较关键差异；图示不替代契约、成本、安全或兼容性证据。

## 选型过程

1. 建立单一决策记录：状态、问题、适用范围、非目标、决策者/需咨询角色、硬约束、成功标准、期限和需要授权的事项。
2. 先定义 decision drivers 及优先级，再形成短名单；保留现状/不引入新技术作为可行选项，先按硬约束淘汰，不以“流行”或单一基准作为结论。
3. 依据同一场景比较兼容性、维护状态、团队维护成本、性能/容量、可靠性、可观测性、安全、许可、迁移与退出成本。新增依赖还需核对直接/传递依赖变化、已知漏洞和许可证，并记录证据对应的版本与观察日期。
4. 对决定性未知项做有明确假设、预算和退出条件的最小可回收验证，例如 API 契约样例、依赖兼容检查或隔离原型；验证不得写入生产配置、凭据或用户数据，结束后不默认保留原型。
5. 输出推荐、备选、放弃项、选择理由、正/负后果、证据、假设、残余风险、实施切片和回退方案；同时定义如何确认实现符合决策，以及哪些版本、负载、成本、安全或组织变化会触发复审或废弃。

## 门禁与交接

- 选型结论必须说明为什么当前推荐满足硬约束、哪些证据可复核、何时需要复审；没有足够证据时输出待决选项，不伪造确定性。
- 评分矩阵仅在指标口径和权重有来源时使用；不得用任意权重或小数分数掩盖证据不确定性。
- 新依赖必须说明版本兼容、许可、安全更新责任、构建/部署影响和移除路径；不得绕过项目依赖管理或本地技术规范。
- 将推荐、备选、风险和待确认事项呈现给用户；用户确认后才写入方案协议并转入 `dev` 常规实现。需要跨角色裁决的结论交给 `survey-corps`，并将依赖和契约影响交给 `cr`、验证重点交给 `qa`、运行与回退输入交给 `dp`。
